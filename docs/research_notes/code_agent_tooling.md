## 1. Aider: is the repo map "PageRank over Tree-sitter tags with lexical false-positive edges"? What would SCIP fix?

### Takeaway
CONFIRMED. `repomap.py` builds a file-level `networkx.MultiDiGraph` where an edge exists from every file that references a name to every file that defines the same name string, then runs personalized `nx.pagerank`. Matching is purely by identifier string, so common names create false edges; Aider only damps this with heuristics (weight multipliers), not with resolution. SCIP-resolved symbols would replace the string join with an exact occurrence-to-definition join.

### Cited Findings
- Tags come from Tree-sitter `.scm` queries; `@name.definition.*` captures become kind `def`, `@name.reference.*` become kind `ref`; results cached in a `diskcache` sqlite cache keyed by file mtime — [repomap.py @5dc9490](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/repomap.py) (imports `diskcache`, `grep_ast`, `networkx` used in `get_ranked_tags`; `get_tags` compares `val.get("mtime") == file_mtime`).
- Graph build (`get_ranked_tags` starts at about line 365): `defines[name] -> set(files)`, `references[name] -> list(files)`; `idents = defines.keys() ∩ references.keys()`; `G = nx.MultiDiGraph()`; for each ident, for each (referencer file, count) and each definer file, `G.add_edge(referencer, definer, weight=use_mul*sqrt(num_refs), ident=ident)` (lines ~475-514). So nodes are FILES, edges carry the identifier string, and the join is a name-string cross product — [repomap.py L475-L514](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/repomap.py#L475-L514).
- Weight heuristics (`mul`, lines ~487-499): x10 if the ident is in `mentioned_idents` (words from the user chat); x10 if snake/kebab/camel case and length >= 8; x0.1 if it starts with `_`; x0.1 if the ident is defined in more than 5 files; x50 if the referencer is a file already in the chat (`chat_rel_fnames`); `num_refs` is `math.sqrt`-damped. Self-edge weight 0.1 for defined-but-never-referenced idents — same file.
- Ranking: `nx.pagerank(G, weight="weight", personalization=..., dangling=...)` (line ~525); personalization gives chat files and files whose path components match mentioned idents extra mass; ZeroDivisionError fallback re-runs without personalization (issue #1536 comment in code). Then rank is redistributed along out-edges proportional to edge weight to get a score per `(definer file, ident)` pair and the map is truncated by a token budget via binary search on the number of tags (`lower_bound/upper_bound/middle`, `middle = min(max_map_tokens // 25, num_tags)`) — same file.
- If `references` is empty the code sets `references = defines` so something is still ranked (same file, ~line 466).
- Python tags query: `reference.call` captures `(call function: (identifier))` and `(call function: (attribute attribute: (identifier)))`, i.e. for `obj.save()` the receiver is discarded and only `save` is recorded as a reference — [python-tags.scm](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/queries/tree-sitter-language-pack/python-tags.scm). Names like `get`, `save`, `run`, `update`, `close` will therefore link every caller file to every file defining such a method (damped only by the >5-definers x0.1 rule). Only calls are references (no attribute reads, no type annotations, no imports).
- TypeScript query has only two reference captures (`@reference.type` for `type_identifier`, `@reference.class` for `new X()`), none for plain function/method calls — [typescript-tags.scm (tree-sitter-languages dir)](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/aider/queries/tree-sitter-languages/typescript-tags.scm). I did not find a `typescript-tags.scm` under the `tree-sitter-language-pack` query dir listing; which dir wins at runtime was not verified.
- When a language's query yields defs but no refs, Aider backfills references from Pygments lexer tokens (`Token.Name` tokens) — `get_tags_raw` code comment "Use pygments to backfill refs" — even cruder than tree-sitter matching.
- Deps are not stdlib: networkx, diskcache, grep_ast, tree_sitter, tree-sitter language pack, pygments, tqdm — import block of repomap.py (same link). pyproject classifiers list Python 3.10-3.13 — [pyproject.toml](https://github.com/Aider-AI/aider/blob/5dc9490bb35f9729ef2c95d00a19ccd30c26339c/pyproject.toml).
- SCIP symbols are fully-qualified, unique identifiers with occurrence roles (definition vs reference), produced by compiler front-ends — [scip.proto, Symbol grammar](https://github.com/sourcegraph/scip/blob/d556dd3c24b3c1787e0b62cd31f25188300e3098/scip.proto#L148-L205). That removes the string-collision false positives, and SCIP records receiver-resolved method references.

### Inferences
- Reusable data model for Planner: `defs[name]->files`, `refs[name]->Counter(files)`, edge weight = base x multipliers x sqrt(count), personalization vector = files named in the ticket. The multiplier table is cheap and valuable; keep it, but key it on a SCIP symbol (or `(file, qualified name)`) when available and fall back to bare names otherwise.
- Stdlib port: PageRank is ~25 lines (power iteration, damping 0.85 as networkx default, dangling mass redistributed to the personalization vector, sum parallel edges). Replace diskcache with a JSON/sqlite3 (stdlib) cache; key the cache on content hash rather than mtime (mtime is coarse on Windows/NTFS, changes after git checkout, and differs across WSL `/mnt/c`). Replace token counting with len/4 or a character budget.
- Pitfall list: (1) edges between FILES only — a 3000-line file with one hot symbol dominates; consider symbol-level nodes. (2) Name collisions inflate hub files (utils, constants). (3) TS/JS function-call edges may be missing (query-dependent; unverified at runtime). (4) Tree-sitter itself is not stdlib; for a stdlib-only Planner the Python side can use `ast` (exact `Name`/`Attribute` nodes, still unresolved), and TS needs an external tool (SCIP or tree-sitter).
- With SCIP, an edge is `occurrence(symbol S, role=reference, file A) -> definition(S, file B)`; no heuristics needed for collisions, and `SymbolInformation.relationships` (implementations/overrides) adds edges tree-sitter cannot see. Cost: needs Node.js and a working project build config, and index freshness; fall back to the Aider-style heuristic graph when the index is stale.

### Gaps
- I did not execute Aider to measure false-positive rates; "false positive for common identifiers" is established by code reading, not by measurement.
- Which of the two query directories is loaded at runtime for TypeScript was not traced.
- Stars/maintenance status of Aider could not be checked (API blocked); last commit on the default branch is 2026-05-22.

## 2. SWE-agent: ACI line navigation + str_replace editing with an immediate syntax gate. How is the gate implemented and how does it fail?

### Takeaway
PARTLY TRUE. The gate is `flake8 --isolated --select=F821,F822,F831,E111,E112,E113,E999,E902` run via `subprocess.run(..., shell=True)`, not tree-sitter. It is a hard rollback gate only in the legacy "windowed" edit bundles (SWE-agent 0.7-era configs); in the current default config (v1.x, `tools/edit_anthropic` str_replace_editor) the linter is OFF unless `USE_LINTER=true` is set, and even when on it only appends a warning after applying the edit. Line-wise windowed navigation is likewise not in the default config.

### Cited Findings
- Gate implementation: `flake8()` returns "" for any non-`.py` file; otherwise runs `registry.get("LINT_COMMAND", "flake8 --isolated --select=F821,F822,F831,E111,E112,E113,E999,E902 {file_path}")` with `shell=True`, capturing stdout — [tools/windowed/lib/flake8_utils.py (~L141)](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/tools/windowed/lib/flake8_utils.py). Selected codes: F821 undefined name, F822 undefined name in `__all__`, F831 duplicate argument, E111/E112/E113 indentation, E999 syntax error, E902 IO error.
- Pre/post diffing: lint is run before the edit and after; errors that existed before are removed after shifting their line numbers by `lines_added = replacement_n_lines - (window_end - window_start + 1)`; previous errors inside the edit window are dropped from the "previous" list (so they are re-reported as new); new errors with `line_number < replacement_window[0]` are ignored ("shadowed by previous errors") — same file, `_update_previous_errors` and `format_flake8_output`.
- Rollback variant: `windowed_edit_linting/bin/edit` runs flake8 before and after, and if new errors exist calls `wf.undo_edit()` and prints "Your proposed edit has introduced new syntax error(s) ... Your changes have NOT been applied", showing both the would-be window and the original window — [tools/windowed_edit_linting/bin/edit](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/tools/windowed_edit_linting/bin/edit). `undo_edit` restores the in-memory `_original_text` — [windowed_file.py](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/tools/windowed/lib/windowed_file.py).
- Which configs use it: `windowed` + `windowed_edit_linting` (WINDOW 100, OVERLAP 2) appear in `config/sweagent_0_7/07*.yaml` and `config/human/*.yaml` — [07.yaml](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/config/sweagent_0_7/07.yaml). `config/default.yaml` bundles only `tools/registry`, `tools/edit_anthropic`, `tools/review_on_submit_m` and sets `USE_FILEMAP: 'true'` — [default.yaml](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/config/default.yaml). A grep for `USE_LINTER` in config/, tools/ and sweagent/ finds it only inside `str_replace_editor` (default `"false"`), never set true in any config.
- In `str_replace_editor` (`USE_LINTER` at ~L33; lint calls at ~L541/L554) the edit is written first (`write_file`), then lint; on new errors it appends `LINT_WARNING_TEMPLATE`: "Your edits have been applied, but the linter has found syntax errors ... In rare cases, the linter errors might not actually be errors" — [str_replace_editor](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/tools/edit_anthropic/bin/str_replace_editor). So no rollback there.
- `str_replace` semantics in that tool: `file_content = read_file(path).expandtabs()` and `old_str/new_str.expandtabs()`; error if 0 occurrences ("did not appear verbatim") or more than 1 (reports line numbers); error if `new_str == old_str`; edit history kept for `undo_edit` — same file (~L519-L540). Because the expanded content is what is written back, tab characters in the whole file are converted to spaces (read from code; not executed).
- Tree-sitter is used only by `tools/filemap` (imports `tree_sitter_languages`, "tree-sitter line numbers are 0-indexed") to print a skeleton of big files — [tools/filemap/bin/filemap](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/tools/filemap/bin/filemap).
- Project status: README says most current development effort is on mini-swe-agent — [README.md](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/README.md).

### Inferences
- Failure modes of the flake8 gate: (1) Python-only; other languages get no gate. (2) Needs flake8 installed in the executor environment (`install.sh` does `pip install flake8`). (3) Error set depends on the interpreter running flake8 (E999 comes from `ast`/compile of that Python version), so a 3.12-only syntax check on a 3.9 flake8 is a false positive. (4) `shell=True` with a formatted path: spaces/quotes in Windows paths break or inject; use `subprocess.run([...], shell=False)`. (5) Only first-order syntax/name errors; F821 produces false positives with star-imports, conditional definitions, builtins injected by frameworks. (6) Line-shift matching is fragile if the edit changes lines before the window or if error messages change text; errors above the window are discarded, so an edit that breaks an earlier-defined name use is missed. (7) The pre-existing broken file case: all errors inside the window count as new. (8) Default v1.x config has no gate at all, so "SWE-agent has an immediate syntax gate" is true of the 0.7-era ACI and the paper, not of today's default.
- Reusable idea for Planner (stdlib): after each executor edit, run a language-specific cheap gate (`compile()`/`ast.parse` for .py is stdlib and needs no flake8), compute `new_errors = errors_after - shift(errors_before, edit_window)`, and either revert or flag; return both the would-be window and the original window in the failure message; instruct "do not re-run the same failed edit". Prefer `ast.parse` (E999 equivalent, no external dependency, interpreter-version-pinned by design) plus optional `python -m pyflakes` if present.
- str_replace uniqueness check (exactly-one match, report all line numbers on ambiguity) is a good low-cost contract for ticket edit operations; do NOT copy the `expandtabs()` behaviour (rewrites tabs globally) and normalise line endings explicitly (Windows CRLF vs LF in WSL repos).

### Gaps
- The original SWE-agent paper's numbers on the lint effect (ablation) were not fetched in this session; claims here are about the code only.
- Whether `LINT_COMMAND` is overridden in any user-facing docs was not checked beyond config/ and tools/.

## 3. moatless-tools: MCTS SearchTree with UCT backpropagation; "git-worktree checkout is slow, OverlayFS better" — evaluate

### Takeaway
UCT claim: PARTLY TRUE — backpropagation exists in `moatless-tools` main but its selector is a trivial "first expandable node"; the real UCT scorer lives in the separate `moatless-tree-search` repo. Worktree claim: FALSE as a description of moatless — neither repo uses `git worktree`; they use clone + `git checkout`/`reset --hard` and an in-memory "shadow mode" file context. The OverlayFS suggestion is technically sound only on Linux (incl. WSL2 on the ext4 side) and needs mount privileges, so it cannot be the baseline for a Windows 11 + WSL2 + container Planner.

### Cited Findings
- `SearchTree._run` loop: `_select` -> `_expand` -> `_simulate` -> `_backpropagate`; `_backpropagate` does `current.visits += 1; current.value += reward` up the parent chain (no discount) — [moatless/flow/search_tree.py (_run ~L95-L135, _backpropagate ~L326-L345)](https://github.com/aorwall/moatless-tools/blob/011ead57a5c81664e9c45e07e1f50b17e695cc63/moatless/flow/search_tree.py#L326-L345).
- `_select` docstring says "using the UCT algorithm" but the code first returns any unexecuted node, then `expandable_nodes = root.get_expandable_descendants()` and delegates to `self.selector.select(...)` (~L181-L215); the only selector in main is `SimpleSelector`: "Selects the first expandable node" — [moatless/selector/simple.py](https://github.com/aorwall/moatless-tools/blob/011ead57a5c81664e9c45e07e1f50b17e695cc63/moatless/selector/simple.py). A repo-wide grep for `ucb|exploration_weight` in main found nothing.
- The full UCT scorer is in moatless-tree-search: `uct_score` = exploitation + exploration + depth bonus - depth penalty + high-value-leaf bonus + bad-children bonus - high-value-child penalty + parent bonus - finished-trajectory penalty + expect-correction bonus + diversity bonus - duplicate-child penalty - duplicate-action penalty; unvisited nodes get `+inf`. Exploration = `exploration_weight * sqrt(ln(parent.visits) / node.visits)` (default weight 1.0, depth_weight 0.8, high_value_threshold 50.0) — [selector.py @bc66ea6 (uct_score L222, exploration L303)](https://github.com/aorwall/moatless-tree-search/blob/bc66ea64e3fe96cf3c90f197b4bab9aaa15e1eb9/moatless/selector/selector.py#L222) (commit bc66ea64e3fe96cf3c90f197b4bab9aaa15e1eb9).
- Exploitation uses the node's OWN reward (`node.reward.value`) unless `use_average_reward=True`, in which case `node.calculate_mean_reward()` = value/visits (node.py ~L452-L460 in moatless-tools). So the backpropagated `value` only feeds UCT when that flag is on — same selector.py (`calculate_exploitation`).
- `calculate_high_value_leaf_bonus` dereferences `node.reward.value` with no None guard (selector.py, same region); possible AttributeError for unevaluated nodes (read, not executed).
- Node state: `Node` has `node_id, parent, children, visits, value, reward, observation, file_context (cloned per node: file_context=self.file_context.clone())` — [moatless/node.py (visits L226, clone L327)](https://github.com/aorwall/moatless-tools/blob/011ead57a5c81664e9c45e07e1f50b17e695cc63/moatless/node.py#L226).
- Repo state handling: `repository.py` has `shadow_mode: bool = Field(default=False, description="Set to true to not write changes to disk.")`; `FileContext` keeps edited content in memory when shadow mode is on — [moatless/repository/repository.py L9](https://github.com/aorwall/moatless-tools/blob/011ead57a5c81664e9c45e07e1f50b17e695cc63/moatless/repository/repository.py#L9). `GitRepository` resets with `git reset --hard HEAD` then `git checkout -f <commit>`; `utils/repo.py` does `git clone --depth 1`, `git fetch --depth 1 origin <commit>`, `git checkout` — [moatless/utils/repo.py](https://github.com/aorwall/moatless-tools/blob/011ead57a5c81664e9c45e07e1f50b17e695cc63/moatless/utils/repo.py). A case-insensitive grep for `worktree|overlayfs|reflink|copytree|cp -a` over `moatless/` in both repos returned no hits.
- Project state: moatless-tools pyproject 0.1.1, `requires-python = "<3.14,>=3.10"`, deps include pydantic, networkx, tree-sitter==0.24.0, gitpython; README sends readers to moatless-tree-search for the paper implementation (SWE-Search, arXiv 2410.20285) — [README.md](https://github.com/aorwall/moatless-tools/blob/011ead57a5c81664e9c45e07e1f50b17e695cc63/README.md). Last commit 2025-09-01.
- OverlayFS facts (kernel doc): upper fs "must support the creation of trusted.* and/or user.* extended attributes" and valid d_type, NFS unsuitable as upper; workdir must be on the same filesystem as upperdir; lower need not be writable and can be read-only or another overlay; "Changes to the underlying filesystems while part of a mounted overlay filesystem are not allowed" (behaviour undefined, no crash); directory rename returns EXDEV by default unless `redirect_dir`; creating a hard link requires copy-up; without `xino` st_ino may change; `userxattr` "is useful for unprivileged mounting"; metacopy must not be used with untrusted layers — [docs.kernel.org overlayfs](https://docs.kernel.org/filesystems/overlayfs.html).
- Unprivileged mounts: the 5.11 overlayfs pull request lists "Allow unprivileged mounting in a user namespace" (operations on underlying layers use the mounting task's privileges) — [LKML 5.11 pull](https://lkml.iu.edu/2012.2/01416.html).
- WSL2: the Microsoft WSL2 kernel config for 6.6 has `CONFIG_OVERLAY_FS=y`, `CONFIG_USER_NS=y`, `CONFIG_EXT4_FS=y`, `CONFIG_XFS_FS=y`, `CONFIG_BTRFS_FS=m`, `CONFIG_9P_FS=y`, `CONFIG_FUSE_FS=y` (kernel 6.6.107.1) — [config-wsl, linux-msft-wsl-6.6.y](https://raw.githubusercontent.com/microsoft/WSL2-Linux-Kernel/linux-msft-wsl-6.6.y/arch/x86/configs/config-wsl).
- Reflink on Windows: block cloning is ReFS-only ("Block cloning is available only on the ReFS file system type beginning with Windows Server 2016"), via `FSCTL_DUPLICATE_EXTENTS_TO_FILE`; source and destination must be on the same ReFS volume, cluster-aligned (4 KB default, 64 KB optional), same integrity-stream setting; since Windows 11 Moment 5 (KB5034848) block cloning occurs natively in supported copy operations — [Microsoft Learn: block cloning](https://learn.microsoft.com/en-us/windows/win32/fileio/block-cloning). The page does not mention NTFS or Dev Drive; (search snippets suggested Dev Drive/ReFS cloning in Windows 11 24H2, not verified from a primary page).

### Inferences
- Verdict on the OverlayFS idea: (a) Windows 11 native: no overlayfs (it is a Linux kernel feature); NTFS has no equivalent usable from stdlib. (b) WSL2: kernel supports it, but upper/work must be on an xattr-capable local fs, so the sandbox must live on the distro's ext4 VHD (`~/...`), not on `/mnt/c` (9p/drvfs; xattr and d_type support there is not established by my sources, treat as unsupported); the mount needs root/`sudo` or a user namespace + `userxattr` (kernel >= 5.11 per the pull request; WSL 6.6 has USER_NS=y); and the lower tree must not change while mounted, so the "base" must be an immutable snapshot, not the live working copy. (c) Unprivileged containers (Docker default, rootless): `mount(2)` needs CAP_SYS_ADMIN, usually dropped, so overlay mounts typically fail unless a user namespace is allowed by the runtime's seccomp/AppArmor; this is background knowledge, not verified from a fetched source. (d) Directory-rename EXDEV and hard-link copy-up quirks can break tools that move directories. So OverlayFS is an optional Linux/WSL accelerator, never the baseline.
- Portable options for per-branch sandboxes ranked: 1) `git worktree add <dir> <rev>` (stdlib via subprocess; all three platforms; shared object store; each worktree is a full checkout so cost is O(files) disk and time; Windows pitfalls: MAX_PATH/`core.longpaths`, file locks when deleting, Defender scanning, never put worktrees on `/mnt/c` when running git inside WSL); 2) reflink copy (`cp --reflink=auto`, ioctl FICLONE on btrfs/XFS-with-reflink; ReFS block clone on Windows; ext4 — the WSL default — has none) as an opportunistic fast path with plain copy fallback; 3) `cp -al` hardlink tree: near-instant and cheap, but any tool that edits in place (open "w") mutates the shared inode and corrupts the base and every sibling — only safe if the executor edits via write-temp-then-rename, which Planner cannot guarantee for external executor tools; also NTFS hardlink count limit and `.git` must be copied not linked. These three points are background knowledge (not fetched this session) except the ReFS facts cited above.
- Data model worth taking: tree of `Node{id, parent, children, action_steps, observation, reward, visits, value, file_context snapshot}` with persisted JSON for resume (`Node.reconstruct` handles dict-tree and flat list); finish checks (`max_cost`, `max_iterations`, `max_finished_nodes`). For a gating orchestrator, plain best-of-N retries with per-attempt snapshots capture most value; UCT only pays off with many parallel attempts and a trustworthy reward (their reward comes from an LLM value function, which is noisy). If implementing UCT, use the textbook form `Q/N + c*sqrt(ln(N_parent)/N)` and fix the two issues above (use backed-up mean; guard None rewards).
- "Shadow mode" idea (edits kept as in-memory patches, applied to disk only for tests) maps well to Planner: store each attempt as a unified diff against a base commit and materialise it in a worktree only when a gate must run.

### Gaps
- SWE-Search paper (arXiv 2410.20285) numbers and claims about worktree speed were not fetched; no source found claiming moatless uses worktrees, so the premise looks like it came from somewhere other than the code.
- Whether OverlayFS works on `/mnt/c` in current WSL2 builds, and rootless-Docker behaviour, were not verified with a primary source. Test with `mount -t overlay` on the actual machine before relying on it.
- Dev Drive/NTFS cloning support unconfirmed.

## 4. debug-gym: pdb tool step cost vs `sys.monitoring` / traceback `f_locals` slicing; Python 3.12 vs 3.10/3.11

### Takeaway
PARTLY TRUE. The tool design does force one debugger action per LLM step and restarts the session after edits, so interactive debugging is step-expensive; but I found no measured step-cost number in sources fetched. `sys.monitoring` exists only on Python >= 3.12, so it cannot be the only mechanism if Planner must support 3.10/3.11; traceback-frame `f_locals` slicing works on all versions but is post-mortem only. Note debug-gym itself requires Python >= 3.12 and its pdb tool works only on Linux.

### Cited Findings
- Package requires `requires-python = ">=3.12"`; README: "conda create -n debug-gym python=3.12" — [pyproject.toml](https://github.com/microsoft/debug-gym/blob/d51a02527f51fac5ccde722db6cb7daa8741a2ef/pyproject.toml), [README.md](https://github.com/microsoft/debug-gym/blob/d51a02527f51fac5ccde722db6cb7daa8741a2ef/README.md).

Only the first command will be executed."; `b`/`break` without args lists breakpoints and `cl` clears all and restarts pdb; PDB sessions restart after a successful edit or an entrypoint change and persistent breakpoints are re-applied (`update_breakpoints`, `on_edit_success`, `on_env_reset`) — [debug_gym/gym/tools/pdb.py](https://github.com/microsoft/debug-gym/blob/d51a02527f51fac5ccde722db6cb7daa8741a2ef/debug_gym/gym/tools/pdb.py). Other tools: bash, edit, eval, grep, listdir, submit, view (tool dir listing).
- `solution_agent` validates each benchmark instance: applies a gold patch, checks tests fail before and pass after, and checks the pdb tool works — README.md.
- Paper: "debug-gym: A Text-Based Environment for Interactive Debugging", Yuan et al., arXiv 2503.21557, submitted 2025-03-27; the abstract page fetched gives no quantitative results — [arXiv abs](https://arxiv.org/abs/2503.21557).

The page does not say whether pdb uses it.

### Inferences
- The "many LLM steps" mechanism is visible in code: one pdb command per call, no scripted multi-command sequence, restart-and-replay of breakpoints after each edit, plus a timeout per command. The sources fetched do not quantify the step overhead; treat the claim as plausible but unmeasured.
- Replacement design for Planner executors (stdlib): run the failing test/command once under a small wrapper that, on exception, walks `tb` frames and records `(filename, lineno, function, repr-truncated f_locals for the innermost N frames)` into JSON — works on 3.10-3.13+ using only `sys.exc_info()/traceback`. This is one tool call instead of an interactive session. Caveats: post-mortem only (no watch on a value before failure); `repr()` can have side effects/be huge — truncate and guard with try/except; locals may contain secrets or PII — redact (Planner's security rules); on 3.13+ `frame.f_locals` for functions is a write-through proxy (PEP 667, from my background knowledge, not fetched — verify), so copy values immediately.
- When to use `sys.monitoring` instead (3.12+ only): record LINE/CALL/RAISE events for chosen files with `DISABLE` on already-seen locations to get a cheap trace of "which lines executed" and the exception origin; use a free tool id (3 or 4) to avoid clashing with `DEBUGGER_ID` (pdb/IDE) and `COVERAGE_ID` (coverage.py sysmon mode). Limits: only 6 tool ids per interpreter; global state, so run in a subprocess; no equivalent on 3.10/3.11, where the fallback is `sys.settrace`/`sys.setprofile` (much slower, per-thread). If Planner's baseline Python is 3.10/3.11 (check `user-context.md`), make 3.12+ features optional with feature detection `hasattr(sys, "monitoring")`.
- Ideas worth lifting from debug-gym beyond pdb: (1) tool classes with lifecycle hooks (`on_env_reset`, `on_edit_success`) so state such as breakpoints survives resets; (2) the gold-patch pre-validation (instance must fail before and pass after) — a ready-made rule for Planner ticket compilation: a ticket's verification command must be shown red on the base and green on a reference solution, otherwise the ticket is rejected; (3) sandboxed terminals (docker/k8s/local) behind one interface.
- Windows 11 native: pdb through a PTY does not work (README); a stdlib `pexpect` replacement does not exist on Windows. Another reason for the one-shot wrapper approach.

### Gaps
- The paper's actual results on pdb-assisted vs non-pdb agents and step counts were not retrieved (abstract only).
- PEP 667 / 3.13 `f_locals` semantics and any 3.14 pdb-on-`sys.monitoring` change are from memory and flagged unverified.

## 5. SCIP: protocol, symbol format, indexers, locking a symbol signature, and the example symbol string

### Takeaway
The example `scip-ts npm @planner/core 1.0.0 domain/escrow#SettlementCommand.` is syntactically parseable under the spec grammar but wrong for a real scip-typescript index: wrong scheme (`scip-typescript`, not `scip-ts`), wrong suffix for a class/interface/type (`#`, not `.`), and missing the file-path namespace descriptors that scip-typescript emits. Correct shape: `scip-typescript npm @planner/core 1.0.0 src/domain/`escrow.ts`/SettlementCommand#` (the path-escaping form is inferred from one snapshot; verify by indexing a sample project).

### Cited Findings
- Grammar (verbatim from scip.proto): `<symbol> ::= <scheme> ' ' <package> ' ' (<descriptor>)+ | 'local ' <local-id>`; `<package> ::= <manager> ' ' <package-name> ' ' <version>`; `<scheme>`, `<manager>`, `<package-name>`, `<version>` are "any UTF-8, escape spaces with double space"; scheme "must not be empty nor start with 'local'"; `.` is the placeholder for an empty manager/name/version; descriptors: namespace `<name>/`, type `<name>#`, term `<name>.`, meta `<name>:`, macro `<name>!`, method `<name>(<disambiguator>?).`, type-parameter `[<name>]`, parameter `(<name>)`; identifier chars `_ + - $` ASCII letters/digits, anything else needs backtick escaping (`` `...` ``, backtick doubled) — [scip.proto L148-L190](https://github.com/sourcegraph/scip/blob/d556dd3c24b3c1787e0b62cd31f25188300e3098/scip.proto#L148-L190).
- Messages: `Symbol{scheme, package{manager,name,version}, descriptors[]}`, `Descriptor.Suffix` enum (Namespace=1, Type=2, Term=3, Method=4, TypeParameter=5, Parameter=6, Meta=7, Local=8, Macro=9) — scip.proto L190-L230 (same link).
- `SymbolInformation` carries `symbol`, markdown `documentation`, `relationships`, `kind`, and `signature_documentation` as a `Signature{language, text, occurrences}` — [scip.proto](https://github.com/sourcegraph/scip/blob/d556dd3c24b3c1787e0b62cd31f25188300e3098/scip.proto) (message `Signature` after `Descriptor`; `SymbolInformation` follows). `Document.relative_path` and `Occurrence.symbol_roles` identify files and definition vs reference occurrences.
- scip-typescript emits scheme `scip-typescript`, manager `npm`, with `.` for empty name/version: `` `scip-typescript npm ${name || '.'} ${version || '.'} ` `` — [src/ScipSymbol.ts](https://github.com/sourcegraph/scip-typescript/blob/ad3ca370efb05d305714c4bc859237ea701e40a4/src/ScipSymbol.ts). Package descriptor = `Suffix.Namespace`, type descriptor = `Suffix.Type` — [src/Descriptor.ts](https://github.com/sourcegraph/scip-typescript/blob/ad3ca370efb05d305714c4bc859237ea701e40a4/src/Descriptor.ts).
- Real scip-typescript snapshot symbols (package/scheme shown abbreviated by the snapshot printer): `src/`property-assignment-reference.ts`/ContextualProperties#`, `.../ContextualProperties#importedShorthand.` (a property is a term `.`), `.../acceptContext().`, `.../acceptContext().(_value)` (parameter) — [snapshots/output/syntax](https://github.com/sourcegraph/scip-typescript/tree/ad3ca370efb05d305714c4bc859237ea701e40a4/snapshots/output/syntax). So the class takes `#`, its field takes `.`, functions `().`, and the file name is a backtick-escaped namespace.
- scip-python symbols: `scip-python python <dist-name> <version> <module path>/<Class>#<method>().` e.g. `scip-python python snapshot-util 0.1 advanced/Test#test().` and `scip-python python python-stdlib 3.11 typing/Generic#`; module init marker `simple/__init__:` — [snapshots/output (pyright-scip)](https://github.com/sourcegraph/scip-python/tree/3b50a0697bddf623f6d879b53bf66b0656309db3/packages/pyright-scip/snapshots/output). README: package names/versions derived from `pip` or supplied by `--environment`; Python 3.10+ supported; needs Node >= 16 — [scip-python README](https://github.com/sourcegraph/scip-python/blob/3b50a0697bddf623f6d879b53bf66b0656309db3/README.md). scip-typescript README: Node v22 and v24 supported (CI source of truth) — [README](https://github.com/sourcegraph/scip-typescript/blob/ad3ca370efb05d305714c4bc859237ea701e40a4/README.md).
- Tooling: `scip` CLI v0.10.0 with commands `lint`, `print`, `snapshot`, `stats`, `test`, `expt-convert` (SQLite) — [docs/CLI.md](https://github.com/sourcegraph/scip/blob/d556dd3c24b3c1787e0b62cd31f25188300e3098/docs/CLI.md). Language bindings in repo: dotnet, go, haskell, java, kotlin, rust, typescript (no Python binding). Indexer list in README: scip-java, scip-typescript, scip-clang, scip-ruby, scip-python, scip-dotnet. DESIGN.md: SCIP is a transmission format, not meant as a query/storage format.
- Repo location: README links now point to `github.com/scip-code/scip` while `git remote` of the clone is `sourcegraph/scip` (redirect presumably) — scip README.

### Inferences
- Checking the example against the grammar: scheme `scip-ts` OK; package `npm @planner/core 1.0.0` OK (slash and `@` allowed in package-name as "any UTF-8"; no spaces); descriptors `domain/` (namespace), `escrow#` (type), `SettlementCommand.` (term) all parse. Problems: (1) scheme mismatch — a verifier comparing against an index produced by scip-typescript will never match `scip-ts`; (2) `SettlementCommand.` says "term" (const/property), but a TS class/interface/type alias is `#`; (3) `domain/escrow#` treats `escrow` as a type, but the indexer emits file-path namespaces with the file name escaped, so the real symbol is expected to be `src/domain/`escrow.ts`/SettlementCommand#` (assuming each directory is its own `name/` descriptor — the snapshot only shows a single `src/` directory; verify with a nested file). 
- Locking a signature in a ticket: store `{symbol: "<full string>", kind: "Class|Function|Method|...", signature_text: "<Signature.text>", signature_hash: sha256(normalised text), locator: relative_path}` in the ticket's frontmatter. Verify later: run the indexer (`npx @sourcegraph/scip-typescript index` / `scip-python index .`), dump with `scip print --json index.scip` (subprocess; stdlib `json`), find `SymbolInformation.symbol == locked symbol`, compare `signature_documentation.text` hash and `kind`, and check there is exactly one definition occurrence. Stdlib alternative to the CLI: hand-decode protobuf (varints/length-delimited, ~100 lines) — doable but brittle; prefer the CLI.
- Lock the descriptors only, not the package version: the version field changes on every package bump (e.g. `1.0.0` -> `1.0.1`), so compare symbols with `package.version` wildcarded (split on the 4th space, remembering double-space escaping). Moving a TS file changes its path-based namespace and so the symbol — treat as "moved", not "deleted", by falling back to a `(kind, name, signature_hash)` match. Python symbols are module-path based and similarly change on module moves.
- Pitfalls: scip-typescript needs Node 22/24 and a resolvable tsconfig/`npm install` state; scip-python needs Node plus a pip environment; both are slow on big repos and absent on a machine without Node — so SCIP must be an optional Planner capability with a stdlib `ast` fallback for Python (exact top-level def/class signature via `ast.get_source_segment` / `ast.unparse` of args). Windows: path separators in `relative_path` are `/` (inferred from the format; verify) and the `scip` CLI has Windows binaries on its releases page (README says "binaries ... here", platform list not read).
- Index freshness: an index is a snapshot; tie it to a git commit (record `git rev-parse HEAD` and `metadata.project_root` in the lock) and re-index at gate time rather than trusting a cached index.

### Gaps
- Exact scip-typescript treatment of nested directories and Windows path separators was not confirmed by running the indexer.
- I did not verify that `scip-ts` is not an alias anywhere (no occurrence found in the scip-typescript source I read).
- Whether the `scip` CLI Windows binary is published for v0.10.0 was not checked.

## 6. Cross-cutting: what to take from each repo, and stdlib/Windows/WSL2/Linux pitfalls

### Takeaway
Take: Aider's weighted, personalized reference graph (heuristic fallback), SWE-agent's pre/post-diffed rollback gate with a precise failure message and uniqueness-checked replace, moatless's persisted attempt-tree + shadow-mode diffs (without full MCTS), debug-gym's tool lifecycle hooks + gold-patch ticket validation + one-shot failure introspection, SCIP's symbol-string lock. Licences are all permissive (MIT or Apache-2.0), so ideas and small reimplementations are fine; copying Apache-2.0 code (Aider, SCIP, scip-typescript, moatless-tree-search) requires keeping licence/NOTICE and marking changes.

- Maintenance signals from commit dates: scip, scip-typescript, scip-python and debug-gym had commits within the week before 2026-10-25; aider's last default-branch commit is 2026-05-22; SWE-agent 2026-07-16 and its README redirects effort to mini-swe-agent; moatless-tools has been quiet since 2025-09-01 (clone logs above).

### Inferences
- Concrete data models/algorithms to port (all stdlib-feasible):
  1. Aider: `Tag(rel_fname, name, kind, line)`; graph as `dict[src_file][dst_file] -> weight` with ident list; power-iteration PageRank with personalization; per-(file, ident) rank spill; budgeted selection by binary search over tag count. Replace tree-sitter with `ast` for Python; for other languages accept SCIP or skip.
  2. SWE-agent: `edit(file, window, new_text)` transaction = {snapshot, apply, gate(before/after), commit-or-rollback, report(would-be window, original window)}; the "errors above the window are ignored" rule is risky — prefer file-level comparison of error multisets after line-shift.
  3. moatless: attempt tree JSON (`id, parent, status, reward, visits, value, patch`) for resumable retries; costs/iteration caps as finish criteria; reward from deterministic gates (tests, lint) rather than an LLM value function.
  4. debug-gym: `Tool.use(env, **args) -> Observation`, plus hooks; ticket pre-validation (red on base, green on gold).
  5. SCIP: symbol-lock records as described in section 5.
- Windows 11 / WSL2 / Linux pitfalls for a stdlib implementation: use `subprocess.run([...], shell=False)` and `pathlib`; normalise to `/` in stored keys; run git and heavy file IO inside the WSL ext4 filesystem rather than `/mnt/c` (9p) — and avoid mixing Windows git and WSL git on the same worktree (line endings, file modes, `core.autocrlf`); `os.replace` for atomic writes works on both but fails on Windows if another process holds the file open; Windows MAX_PATH for deep worktree/temp paths (`git config core.longpaths true`, short worktree root); mtime resolution differs (use content hashes for caches); `signal`-based timeouts do not exist on Windows (use `subprocess` timeouts and `taskkill /T` / process groups); PTY/`pexpect`/pdb interactivity unavailable natively on Windows; `fcntl` (FICLONE) is Linux-only; hardlinks (`os.link`) work on NTFS but editing through them aliases content.
